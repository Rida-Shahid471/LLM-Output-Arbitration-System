# LLM Output Arbitration System

## 1. Project Overview

The LLM Output Arbitration System is an AI engineering system designed to audit and evaluate an already-generated Large Language Model (LLM) answer.

The system does not primarily generate a new answer. Instead, it receives an original question or prompt together with a candidate LLM answer and evaluates that answer using multiple independent specialist critics.

The system uses three critics:

1. Factual Accuracy Critic
2. Logical Consistency Critic
3. Completeness Critic

The reports produced by the critics are collected and compared. If the critics disagree, the system detects the disagreement and sends the relevant information to an adjudicator.

The adjudicator reviews the original question, candidate answer, critic reports, and disagreements and produces a final structured verdict.

---

## 2. Problem Statement

Large Language Models can produce answers that contain factual errors, logical problems, or missing information.

Using only one evaluator can make it difficult to identify different types of problems reliably.

This project addresses this problem by using multiple specialized critics. Each critic focuses on a different quality dimension of the candidate answer.

The system then combines the independent evaluations and uses an adjudication stage to resolve disagreements and produce a final assessment.

---

## 3. Project Objective

The main objective of this project is to build a system that can:

- Receive an original question or prompt.
- Receive an already-generated candidate LLM answer.
- Evaluate the candidate answer using three independent critics.
- Produce structured reports from each critic.
- Detect disagreements between critics.
- Resolve important disagreements through an adjudicator.
- Produce a final structured verdict.
- Store arbitration results for later retrieval.
- Provide the results through an API and user interface.
- Support analytics and evaluation of the arbitration system.
- Provide a reproducible deployment using Docker.

---

## 4. Input

The system accepts two primary inputs:

### 4.1 Original Prompt

The original question or instruction that was given to the LLM.

Example:

"What is the capital of Australia?"

### 4.2 Candidate LLM Output

The answer generated by the LLM for the original prompt.

Example:

"The capital of Australia is Sydney."

The system evaluates the candidate output against the original prompt.

---

## 5. Output

The system produces a structured arbitration result containing:

- Arbitration ID
- Original prompt
- Candidate LLM output
- Factual Accuracy Critic report
- Logical Consistency Critic report
- Completeness Critic report
- Detected disagreements
- Overall quality score
- Final confidence
- Confirmed issues
- Dismissed flags with reasons
- Final summary

---

## 6. Critic Layer

The system contains three independent specialist critics.

### 6.1 Factual Accuracy Critic

The Factual Accuracy Critic evaluates whether claims in the candidate answer are factually correct and internally consistent.

The critic should identify factual problems and provide evidence for reported issues.

The critic produces:

- A score from 1 to 5
- Identified issues
- Evidence quotes
- Severity
- Confidence

---

### 6.2 Logical Consistency Critic

The Logical Consistency Critic evaluates whether the reasoning in the candidate answer is logically consistent.

The critic checks for:

- Contradictions
- Unsupported conclusions
- Broken reasoning
- Conclusions that do not follow from the provided reasoning

The critic produces:

- A score from 1 to 5
- Identified issues
- Evidence quotes
- Severity
- Confidence

---

### 6.3 Completeness Critic

The Completeness Critic evaluates whether the candidate answer addresses all important requirements contained in the original question.

The critic checks for:

- Missing parts of the question
- Unanswered requirements
- Partial answers
- Important omissions

The critic produces:

- A score from 1 to 5
- Identified issues
- Evidence quotes
- Severity
- Confidence

---

## 7. Critic Reports

Each critic produces a structured report.

A critic report contains:

- Evaluation dimension
- Score from 1 to 5
- Issues
- Evidence
- Severity
- Confidence

The reports must use structured output so that they can be compared programmatically.

---

## 8. Orchestration

The system will use LangGraph as the orchestration layer.

The three critics should be executed independently and in parallel where possible.

The basic orchestration flow is:

Input
→ Parallel Critics
→ Critique Collection
→ Disagreement Detection
→ Adjudication
→ Final Verdict

The orchestration layer will maintain the state required by the pipeline.

The state will eventually contain information such as:

- Original prompt
- Candidate output
- Critic reports
- Disagreements
- Final verdict
- Errors

---

## 9. Disagreement Detection

The system will compare the reports generated by the three critics.

A disagreement may be detected when:

- Critics disagree about whether an issue exists.
- Severity differs significantly.
- One critic identifies an issue that other critics do not identify.
- Critic scores differ significantly.
- Evidence or issue categories conflict.

The disagreement detector will produce a structured disagreement report.

---

## 10. Adjudication

The adjudicator receives:

- Original prompt
- Candidate answer
- All critic reports
- Detected disagreements

The adjudicator does not simply average critic scores.

Instead, it evaluates the available evidence and resolves conflicts.

For factual disagreements, the adjudicator considers the evidence supporting the factual claim.

For logical disagreements, the adjudicator examines the reasoning and whether the conclusion follows.

For completeness disagreements, the adjudicator checks the original question and determines whether all required parts were addressed.

---

## 11. Final Verdict

The adjudicator produces a structured final verdict.

The final verdict contains:

- Overall quality score from 1 to 10
- Final confidence
- Confirmed issues
- Dismissed flags
- Reasons for dismissed flags
- Final summary

The final verdict represents the result of the complete arbitration process.

---

## 12. Persistence

The system will store arbitration records so that previous results can be retrieved without running the LLM evaluation pipeline again.

The project will use SQLite and/or JSON-based audit storage during development.

Stored records will allow the system to maintain an audit history.

---

## 13. API

The project will expose the arbitration functionality through FastAPI.

The main API endpoints are:

### POST /v1/arbitrate

Used to submit one candidate answer for arbitration.

### POST /v1/arbitrate/batch

Used to submit multiple candidate answers for arbitration.

### GET /v1/arbitrations/{id}

Used to retrieve a previously stored arbitration result.

Additional endpoints may be added later if required.

---

## 14. User Interface

The project will provide a user interface for exploring arbitration results.

The interface should allow users to view:

- Original prompt
- Candidate answer
- Final score
- Confidence
- Final summary
- Critic reports
- Disagreements
- Evidence for issues

The first version may use Streamlit for faster development.

## 15. Analytics

The project will include analytics for understanding critic behavior and system performance.

The analytics layer will track information such as:

- Which critic identifies the most issues
- Which critic is overruled most often
- Common issue types
- Critic agreement rate
- Critic disagreement rate
- Critic latency
- Total arbitration latency
- Scores
- Overrides

---

## 16. Evaluation

The project will include an evaluation dataset containing different types of candidate answers.

The dataset should include:

- Factual errors
- Logical contradictions
- Incomplete answers
- Correct answers
- Mixed-quality answers
- Ambiguous cases

The evaluation process should be repeatable.

Evaluation results should be based on measured data rather than invented performance numbers.

---

## 17. Reliability and Failure Handling

The system should handle failures safely.

Expected failure scenarios include:

- LLM provider errors
- Timeouts
- Malformed structured outputs
- Individual critic failures
- API errors
- Database errors

The system should retry appropriate failures.

If one critic fails after retries, the remaining critics should still be able to continue where possible, and the final confidence should be reduced or appropriately annotated.

---

## 18. Deployment

The final project will use Docker for reproducible deployment.

The deployment setup should include the required project services and configuration.

Secrets such as API keys must not be hard-coded into the source code.

Environment variables should be used for sensitive configuration.

An `.env.example` file will document required environment variables without exposing real secrets.

## 21. Required Demonstration Cases

The project will demonstrate at least four important cases:

### Case 1 — Factual Error

The candidate answer contains an incorrect factual claim.

### Case 2 — Logical Flaw

The candidate answer contains incorrect or unsupported reasoning.

### Case 3 — Incomplete Answer

The candidate answer fails to address one or more requirements of the original question.

### Case 4 — Good Answer

The candidate answer is correct, logically consistent, and sufficiently complete.
